# shall-we

[whats-wrong](whats-wrong.md)에서 정의한 Step을 TDD로 하나씩 구현한다. 검증은 [is-it-ok](is-it-ok.md).

## 진행

- is-it-ok 보고서의 필수 수정 항목을 먼저 고친다. 선택 항목은 사용자가 요구할 때만 고친다.

- Plan의 Step을 하나씩 처리하고 Step마다 커밋한다.
- Red → Green → Refactor. 테스트 통과로 끝내지 않고 리팩터링으로 코드를 개선한다.
- 리팩터링 중에는 테스트를 계속 통과시키되 범위를 넓히지 않는다.

## 테스트

- 불필요하거나 의미 없는 테스트를 늘리지 않는다.
- 커버리지 80%는 목표가 아니라 점검 기준이며, 새로 바뀐 코드에만 적용한다.
- 미달이면 테스트를 늘리기 전에 커버되지 않은 부분과 그 이유를 먼저 확인한다.

## 구현 원칙

- 필요 최소한으로 구현한다. 오버 엔지니어링 금지.
- UI는 불필요한 세컨더리 라벨이나 설명을 피하고 정보 구조와 레이아웃으로 전달한다.
- 요구사항을 위해 바꾼 코드 외에는 가급적 건드리지 않는다. 근본 원인 수정에 주변 변경이 필요하면 허용하되, 이유를 제시하고 영향 범위를 검증한다.

## 익숙하지 않은 기능

제로 베이스로 바로 만들지 않고, 먼저 GitHub에서 활발히 유지보수되고 라이선스가 명확한 유사 오픈소스를 찾아 비교한다.

| 확인 항목 |
|---|
| 유지보수 상태 |
| 라이선스 |
| 현재 프로젝트와의 호환성 |
| 구현 복잡도 |
| 알려진 결함 |

- 스타 수만으로 선택하지 않는다.
- 호환되지 않거나 출처가 불분명한 코드는 직접 복사하지 않는다.
- 적합한 결과가 없으면 이유를 남기고 직접 구현한다.

## 중단 조건

명세가 모호하거나 코드와 충돌하면 추측하지 않고 멈추고 묻는다.
